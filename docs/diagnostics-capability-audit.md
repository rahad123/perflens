## Collection and analysis path

The CLI runs bounded k6 profiles and leaves raw JSON samples under each run. `packages/cli/src/audit/results.ts` derives profile and per-endpoint request metrics, including HTTP status maps. `packages/node-instrumentation/src/index.ts` starts OpenTelemetry HTTP and PostgreSQL instrumentation before the consumer loads its modules; `packages/node-instrumentation/src/express.ts` adds Express route spans. The analysis service queries Tempo by service, run ID, profile, and profile window, then persists sanitized traces under `analysis/evidence.json`. The analysis engine evaluates the current deterministic Phase 3 rules over those traces and profile metrics. Reporting consumes only the stored run, result, analysis, and evidence artifacts; it does not query Prometheus or Tempo.

Prometheus is a real component in the local stack: its packaged scrape config targets the consumer base URL’s `/metrics`, and the reference apps expose process defaults plus PerfLens request counters/histograms. The provisioned dashboard uses those metric names. However, no selected audit-window query is copied into run artifacts, and the generic instrumentation preload does not provide process metrics. Therefore current Prometheus availability or dashboard data must not be represented as per-run CPU/memory measurements.

## Phase 7.1 diagnostic evidence model

Phase 7.1 does not change the Phase 2 `schemaVersion: 1` profile-result or Phase 3 evidence formats. Those already persist the required HTTP status and endpoint metrics plus correlated trace spans. The report model advances to `reportVersion: 3` and adds `diagnosticEvidence.schemaVersion: 1`, derived without mutating source artifacts. It includes profile/endpoint status records with `results/<profile>.json` source references and coverage records with evidence/analysis source references where applicable. Status counts are compared with the corresponding request count; disagreements are labeled incomplete instead of silently normalized. Historical schema-v1 runs remain readable; missing status maps render as Not persisted.

Coverage states distinguish Available, Partial, No observations, Not collected, Not persisted, Unavailable, and Incomplete. A zero count is shown as “No observations” only when the corresponding evidence snapshot is available. CPU, process memory, container resources, and pool metrics are “Not collected”; no observations of Redis spans are not called “not instrumented.”

## Planned implementation sequence

These are recommendations for later planning only; they are not implemented here.

1. **Phase 7.2 — Runtime Resource Diagnostics:** define a per-run sampling contract and source references first; collect bounded process CPU, RSS, heap, and supported container measurements at profile boundaries; persist timestamped samples; only evaluate pressure when collection coverage, duration, and repeatability support it. Add no saturation claims based solely on one sample.
2. **Phase 7.3 — PostgreSQL Diagnostics:** extend current span evidence with endpoint-to-query grouping and explicit pool instrumentation only where the selected PostgreSQL client exposes a stable API. Preserve normalized SQL and existing repeated/slow-operation rules; expose pool coverage separately from query evidence.
3. **Phase 7.4 — Redis and External Dependency Diagnostics:** add a supported Redis OTel instrumentation integration, map spans to request traces, and report per-request latency/failure consistency for external services. Keep missing spans distinct from zero latency and avoid call-count weighting.
4. **Phase 7.5 — Rich Diagnostic Reporting:** build visualizations only on persisted, source-linked evidence from the prior phases; add trace navigation where stable links can be verified; introduce remediation ordering only after evidence-backed recommendation semantics are specified and separately reviewed.

## Limits

The report is a view over one completed local audit. It does not prove production behavior, resource saturation, endpoint correctness, use/non-use of Redis, or cause of a particular HTTP status. HTTP 429 is described as a too-frequent rejection and lists possible sources without selecting a responsible component. Status distributions add diagnostic context only; they do not alter Phase 3 severity, confidence, thresholds, or rule IDs.
