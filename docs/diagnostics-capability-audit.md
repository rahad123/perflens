## Collection and analysis path

The CLI runs bounded k6 profiles and leaves raw JSON samples under each run. `packages/cli/src/audit/results.ts` derives profile and per-endpoint request metrics, including HTTP status maps. `packages/node-instrumentation/src/index.ts` starts OpenTelemetry HTTP and PostgreSQL instrumentation before the consumer loads its modules; `packages/node-instrumentation/src/express.ts` adds Express route spans. The analysis service queries Tempo by service, run ID, profile, and profile window, then persists sanitized traces under `analysis/evidence.json`. The analysis engine evaluates the current deterministic Phase 3 rules over those traces and profile metrics. Reporting consumes only the stored run, result, analysis, and evidence artifacts; it does not query Prometheus or Tempo.

Prometheus is a real component in the local stack: its packaged scrape config targets the consumer base URL’s `/metrics`, and the reference apps expose process defaults plus PerfLens request counters/histograms. The provisioned dashboard uses those metric names. No selected audit-window query is copied into run artifacts, so Prometheus availability or dashboard data must not be represented as per-run resource measurements. Phase 7.2 separately samples supported Node processes and the selected Compose application container into run artifacts.

## Evidence model

Phases 7.1–7.2 do not change the Phase 2 `schemaVersion: 1` profile-result or Phase 3 evidence formats. Those already persist the required HTTP status and endpoint metrics plus correlated trace spans. The report model advances to `reportVersion: 4` and includes `diagnosticEvidence.schemaVersion: 1` plus `resourceDiagnostics.schemaVersion: 1`, derived without mutating source artifacts. The separate per-run resource artifact uses `schemaVersion: 1`, contains run/profile/timestamp/source/unit metadata, raw process and selected-container samples, and explicit collection states. Historical runs without resource files remain readable and show Not collected; old profile results remain schema v1.

Coverage states distinguish Available, Partial, No observations, Not collected, Not persisted, Unavailable, Incomplete, and Insufficient evidence. Process CPU percentage is process user+system CPU time delta divided by monotonic elapsed time, normalized to one logical CPU; it is not host CPU utilization. Docker CPU is kept separate on the Docker-reported basis and is not presented as quota-normalized. CPU profile summaries require at least two valid samples. Memory uses bytes internally and displays MiB; an unknown/unlimited Docker memory limit remains unavailable rather than zero. A zero count is shown as “No observations” only when the corresponding evidence snapshot is available. No resource findings are emitted in 7.2; metrics are descriptive and do not imply saturation or causation.

## Planned implementation sequence

Phase 7.2 deliberately adds no resource-pressure finding. The following recommendations are for later planning only; they are not implemented here.

1. **Phase 7.3 — PostgreSQL Diagnostics:** extend current span evidence with endpoint-to-query grouping and explicit pool instrumentation only where the selected PostgreSQL client exposes a stable API. Preserve normalized SQL and existing repeated/slow-operation rules; expose pool coverage separately from query evidence.
2. **Phase 7.4 — Redis and External Dependency Diagnostics:** add a supported Redis OTel instrumentation integration, map spans to request traces, and report per-request latency/failure consistency for external services. Keep missing spans distinct from zero latency and avoid call-count weighting.
3. **Phase 7.5 — Rich Diagnostic Reporting:** build visualizations only on persisted, source-linked evidence from the prior phases; add trace navigation where stable links can be verified; introduce remediation ordering only after evidence-backed recommendation semantics are specified and separately reviewed.

## Limits

The report is a view over one completed local audit. It does not prove production behavior, resource saturation, endpoint correctness, use/non-use of Redis, or cause of a particular HTTP status. HTTP 429 is described as a too-frequent rejection and lists possible sources without selecting a responsible component. Status distributions add diagnostic context only; they do not alter Phase 3 severity, confidence, thresholds, or rule IDs. CPU and memory samples are descriptive only; no resource-pressure findings are emitted in Phase 7.2.
