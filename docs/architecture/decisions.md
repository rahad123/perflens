# Phase 1 architecture decisions

- **CLI product, separate test target:** `packages/cli` is the PerfLens developer toolkit. The existing NestJS app and PostgreSQL are a test target. The CLI controls the four existing observability services; it does not own framework integration yet. See [current/future architecture](architecture.md).
- **TypeORM and PostgreSQL:** explicit schema migration, foreign keys, indexes, and integer money values. Automatic schema synchronization is disabled. Migration and seed run before readiness. Local fixtures seed only an empty database and use a transaction/advisory lock; they are not a general data reconciliation system.
- **Clean ordinary paths:** validated DTOs, bounded pagination, joined item/product reads, bulk product validation, and transactional order writes. The deliberately inefficient SQL and N+1 loop live in the explicitly named performance controller.
- **Preloaded OpenTelemetry:** HTTP and pg libraries are patched before Nest loads. OTLP HTTP goes to the Collector, which batches and forwards to Tempo over gRPC. The loopback fixture uses real HTTP so client/server propagation can be examined without an internet dependency.
- **Prometheus metrics:** a small middleware records completed requests with method, route template, and status. A histogram supports quantiles. `@prometheus-io/client` adds Node/process metrics. Metrics are scraped directly; no duplicate OTLP metrics pipeline or metrics generator is needed.
- **Local persistence:** named volumes for PostgreSQL, Tempo, Prometheus, and Grafana. Loopback host ports and anonymous local Grafana Explore keep startup simple without introducing product authentication.
- **Tempo compatibility:** pin the maintained 2.10 patch line for its compact monolithic local-storage configuration. Moving to Tempo 3 is a separate configuration migration, not a reason to add distributed infrastructure to Phase 1. [Tempo 2.10.8 release](https://github.com/grafana/tempo/releases/tag/v2.10.8).
- **Version reproducibility:** exact resolved Node dependencies are recorded in the pnpm lockfile and infrastructure images use explicit release tags. NestJS/TypeORM/OpenTelemetry versions were checked against npm metadata. See [OpenTelemetry initialization guidance](https://opentelemetry.io/docs/languages/js/libraries/), [NestJS TypeORM integration](https://docs.nestjs.com/data/typeorm), and the [Prometheus release](https://github.com/prometheus/prometheus/releases/tag/v3.15.0).

The slow query is bounded to 100 orders and database statements time out after 15 seconds. The N+1 endpoint is bounded to 20 orders. The simulated dependency has a five-second client timeout. These bounds keep the teaching examples manageable; they are not production resource controls.

- **Commander and JSON:** a real executable package uses Commander for argument parsing and a minimal, non-executable JSON target config. Safe initialization never overwrites config or edits source.
- **Non-destructive lifecycle:** reuse the existing Compose definition and a four-service allowlist. Stop preserves all volumes and leaves target services untouched. Probe readiness through Prometheus rather than depending on NestJS.
- **Local-only defaults:** reject remote Docker contexts and target URLs; disable Grafana/Tempo reporting and automatic Grafana update/plugin downloads. Explicit image/dependency downloads still require registry access.
